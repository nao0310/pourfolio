# コーヒー記録・分析・提案アプリ 設計草案

2026年11月18日版 · 図と優先度ドロップダウン付きのClaude Docs版：https://claude.ai/artifact/LHwJJQrf5Vt4rbrL5UNWxL

## 1. 概要

ハンドドリップ1杯ごとの「抽出データ」と「味のフィードバック」を蓄積し、次の1杯の直し方・今日淹れる豆・次に買う豆までを根拠付きで提案するアプリを、サーバー不要の単一HTMLから段階的に育てる設計です。

**仮称**：Pourfolio（ポアフォリオ）。pour（注ぐ）× portfolio（資産）で、抽出記録と手持ちの豆を「育てる資産」として扱う意味です。別案は「珈琲ラボノート」「Brew Ledger」。

### この草案で置いた前提

- 費用：**完全無料**。個人利用なので、サーバー代・有料API・サブスク・追加機材の購入なしで全機能が動くことを必須条件にする
- 利用者：自宅でハンドドリップする本格派の個人（自分専用）
- 購入先：豆は[珈琲問屋オンラインストア](https://www.tonya.co.jp/shop/)で買う。受注後焙煎・焙煎度8段階・生豆時の重量表記などに合わせる（4.4）
- 端末：抽出中はスマホ、分析や書き出しはPCでも使う
- 構成：1ファイルのHTMLで完結。データは端末内に保存し、いつでもファイルに書き出せる。スマホで使うときは無料の静的ホスティングに置く（10章）
- 対象：透過式（V60、カリタウェーブ、オリガミ等）が中心。浸漬式・ハイブリッド（ハリオ スイッチ等）も同じデータ構造で扱う

前提が違う場合は、12章「決めておきたいこと」で切り替えます。

### コンセプト：1杯ごとに賢くなるループ

「淹れる → 味わう → 学ぶ → 提案する → また淹れる」を1杯ごとに回します。豆の在庫はこのループの燃料で、書き出し・共有機能はループの外へ価値を運ぶ出口です。

（図：豆と在庫 → 淹れる → 味わう → 学ぶ → 提案する → 淹れる…と1杯ごとに1周するループ。学ぶ → 書き出し・共有へも出力）

### 設計原則（こだわりの核）

1. **お金がかからない**：有料API・クラウド・課金を使わない。分析も提案もブラウザの中で計算し、AIに相談したいときは「相談用テキスト」をコピーして手元のチャットに貼る
2. **機材を買わなくても本格的**：屈折計やBluetoothスケールがなくても、味の評価だけで診断と提案が動く。機材連携は「手持ちがあれば使える」追加機能
3. **濡れた片手で操作できる**：抽出中は大きなボタン、音声と振動の注湯ガイド、画面スリープ防止
4. **3タップから本格評価まで**：最短は★評価と一言タグだけ。必要なときだけSCA準拠の詳細評価まで掘れる
5. **業界標準に合わせる**：SCAの新評価方式（CVA）、フレーバーホイール、TDS・抽出収率の定義に準拠し、プロのデータと比較できる
6. **「強さ」と「好み」を分けて記録する**：酸味が強いことと、酸味が好きなことは別。ここが提案精度の核心
7. **提案には必ず根拠を添え、変えるのは1変数だけ**：「なぜ挽き目を1段階細かくするのか」を自分のデータと抽出理論で示し、再現できる実験の形で出す
8. **データは自分のもの**：端末内保存（ローカルファースト）、完全なJSON/CSV書き出し、公開されたデータ形式

## 2. 調査サマリー：プロ基準と既存アプリ

プロ水準にする鍵は、「味の強さと好みを分けて記録し、固定の理想ではなく自分の理想ゾーンを学習し、濃度と抽出収率の言葉で直し方を示す」ことです。既存アプリはタイマーと記録が中心で、この診断と在庫計画が手薄です。

### 2.1 業界標準・研究と設計への反映

| 調査で分かったこと | アプリへの反映 |
| --- | --- |
| SCAは2024年、2004年のカッピング方式に代わる新評価方式CVA（SCA-102/103/104）を正式採用。味の描写（何がどれだけ強いか）と、品質の印象（どれだけ良いか）を分けて評価する（[SCA](https://sca.coffee/sca-news/sca-new-cva-cupping-standards)） | テイスティング入力を「強さ」と「好み」の2軸に分ける |
| CVAの描写評価は強度を0〜15で付け（[評価用紙](https://library.sweetmarias.com/wp-content/uploads/2025/06/SCA-CVA-Forms-English-May-2025.pdf)）、香味はフレーバーホイール（2016年版）内側の9カテゴリからCATA（当てはまるもの全部にチェック）で選ぶ。情動評価は9段階（[Kaffeemacher](https://kaffeemacher.ch/en/blogs/kaffeewissen/coffee-value-assessment)） | 強度は0〜15（簡易モードは5段階に丸める）、好みは9段階、香味はタップ式のCATA |
| 1957年の古典的な抽出チャートの理想域は抽出収率18〜22%・濃度（TDS）1.15〜1.35%。UC Davisの新チャートでは、甘さは低濃度・低収率側、苦味は高濃度・高収率側に寄る（[Fresh Cup](https://freshcup.com/why-the-new-coffee-brewing-control-chart-is-a-big-deal/)） | TDS×抽出収率の散布図に自分の高評価点を重ね、「自分の好きゾーン」を表示 |
| 消費者118人の研究では好みが2つの集団に分かれ、主に濃度（TDS）で好みが分かれた。チャートの「理想」は見直すべきと結論（[Cotter ほか 2021](https://www.pubmed.gov/33340109/)） | 固定の理想ではなく、自分の評価から理想ゾーンを学習。「濃い・薄い」の調整を最優先のレバーにする |
| 濃度と抽出収率を揃えると、湯温の違いは味にほとんど影響しなかった（[UC Davis 2020](https://www.teaandcoffee.net/news/25527/new-study-finds-negligible-impact-of-coffee-brewing-temperature-on-sensory-quality/)） | 湯温は「抽出収率を動かす手段」として扱い、提案は濃度と収率の言葉で説明する |
| 抽出収率 = 抽出された成分の重さ ÷ 粉量（[Barista Hustle](https://www.baristahustle.com/?p=770)）。透過式で粉に残る液体は粉1gあたり約2g、浸漬式は約3g（[Barista Hustle](https://www.baristahustle.com/?p=946)） | 屈折計の値から自動計算。抽出液を量っていなければ「湯量 − 2×粉量」で推定し、器具ごとに実測で補正 |
| SCAAの水の基準（2009年）：TDS 150mg/L（75〜250）、カルシウム硬度 68mg/L（17〜85）、アルカリ度 40mg/L前後、pH 7.0（6.5〜7.5）、ナトリウム 10mg/L前後、塩素 0（[SCAA](https://cdn.shopify.com/s/files/1/0561/9102/5336/files/water-standards.pdf)） | 水プロファイルを登録し、基準との差を表示 |
| 冷えた豆ほど細かく均一に挽ける（バース大学などの研究チーム, Scientific Reports, 2016）（[Sci.News](https://www.sci.news/othersciences/physicalchemistry/chill-coffee-beans-tastier-beverage-03951.html)） | 「冷凍のまま挽いたか」を記録し、同じ目盛りでも挽き目が変わる前提で提案する |
| 焙煎後の休ませ期間（レスト）は焙煎度で違う。フィルターの目安は浅煎り約5〜12日、中煎り3〜10日、深煎り1〜5日（[Simon & Bearns](https://simonandbearns.coffee/en/blogs/kaffeeblog/coffee-degassing-how-long-to-rest-filter-coffee-and-espresso)）。14日以上を勧める浅煎りの焙煎所もある（[Coffee Magazine](https://magazine.coffee/blog/9/7091/is-your-coffee-too-fresh)） | 焙煎日から「飲み頃ウィンドウ」を表示し、自分の評価データで豆・焙煎度ごとに補正 |
| 4:6メソッド（2016年ワールドブリュワーズカップ王者・粕谷哲氏）は湯量を40%と60%に分け、前半で甘さと酸味のバランス、後半で濃度を調整する（[コーヒー豆研究所](https://coffee-labo.co.jp/recipe/v60-46-method/)、[Pull & Pour](https://pullandpourcoffee.com/?p=8110)） | 「狙う味 → 注湯配分」を自動計算するレシピテンプレートとして搭載 |
| 日本食品標準成分表では、コーヒー浸出液（粉10g・熱湯150mL）のカフェインは100mL当たり60mg（[食品安全委員会](https://www.fsc.go.jp/visual/kikanshi/k_index.data/vol51_P2_3.pdf)） | 抽出液量と比率から1杯ごとのカフェイン推定値を記録・集計 |

### 2.3 このアプリの勝ち筋

1. **診断型の提案**：自分の履歴と抽出理論から、「なぜ・何を・どれだけ」変えるかを根拠付きで示す
2. **強さと好みの分離**：CVA準拠の2軸評価から、自分だけの理想ゾーンを学習する
3. **在庫計画**：在庫・飲み頃・消費ペースから「今日どれを淹れるか」「いつ買い足すか」を決める
4. **ロックインなし**：完全ローカル・無料・データ形式公開。いつでも全データを持ち出せる

## 4. 記録機能の詳細

記録は「抽出」「テイスティング」「豆と在庫」「器具と水」の4つで、どれも最小入力から始めて後から深掘りできる2段構えです。抽出1回の記録は最短3タップ・30秒以内を目標にします。

### 4.1 抽出の記録

| 項目 | 記録の仕方 |
| --- | --- |
| 豆（必須） | 在庫一覧から選ぶ。前回の豆が初期値 |
| 粉量（必須） | g、0.1g単位 |
| 湯量（必須） | g。比率を入れると自動計算、逆も可 |
| 挽き目（必須） | グラインダーと目盛り。前回値から±ボタンで増減 |
| 湯温 | ℃。よく使う温度をプリセット |
| 蒸らし | 湯量・時間・攪拌の有無。タイマーで自動記録 |
| 注湯ステップ | 開始時刻・累計g・注ぎ方（中心、円、スワール等）。タイマーのラップで実績を記録 |
| 総抽出時間（必須）・落ち切り時間 | 秒。タイマーから自動 |
| 抽出液の重さ・TDS | g・%。量ったときと、屈折計があるときだけ |
| 器具・水 | ドリッパー・フィルター・ケトル・水プロファイル。前回値を引き継ぐ |
| 豆の状態 | 常温／冷凍のまま挽いた／解凍してから挽いた |
| 状況 | 日時（自動）、気分、目的（目覚め・集中・くつろぎ・来客） |
| 写真・メモ | 粉、注湯中の粉の層、抽出液の色。音声入力も可 |

自動で計算する値：比率、焙煎後日数、抽出収率（TDSがあるとき）、1杯の原価、カフェイン推定量。

- 前回との違いを色で示し、2つ以上の条件を同時に変えたら「比べにくくなります」と知らせる
- 計画（レシピ）と実績を並べて保存し、ズレが大きかった項目は次回のガイドで強調する

### 4.2 テイスティング（3段階）

| 段階 | 時間の目安 | 入力する内容 | 使いどころ |
| --- | --- | --- | --- |
| クイック | 約10秒 | 総合★1〜5と一言タグ（酸っぱい・苦い・薄い・濃い・渋い・甘い・好き） | 毎日の記録 |
| 標準 | 約30秒 | 濃さ・酸味・苦味・甘さ・ボディ・渋みを「弱すぎ −2／ちょうど良い 0／強すぎ +2」で評価（JAR方式）＋総合 | ダイヤルインの診断 |
| プロ | 2〜3分 | 香り（粉・液）・風味・余韻・酸味・甘さ・口当たりの「強度0〜15」と「好み1〜9」を別々に。香味はCATAで選び、熱い・温かい・冷めたの3温度で記録 | 豆の評価・比較・ブラインド |

- JAR方式は「自分にとって弱すぎるか強すぎるか」を直接聞くので、0からのズレがそのまま直す方向になる（6章）
- 香味の9カテゴリ：フローラル／フルーティ／酸っぱい・発酵／グリーン・植物／ロースト／スパイス／ナッツ・ココア／甘い／その他。各カテゴリから細かい語（ベリー、柑橘、ジャスミン等）へ掘り下げられる
- 雑味タグ：えぐい、紙っぽい、焦げ、古い（酸化）、水っぽい。診断の手がかりにする
- 冷め際の評価は、抽出完了から5分後・15分後に画面内で入力を促す（通知は対応端末のみ）

### 4.3 豆と在庫

- 豆カードの項目：銘柄、購入先、商品ページURL、生産国・地域・農園・生産者、品種、精製方法、標高、収穫年、焙煎度、焙煎日、注文日・到着日、表記重量と実重量、価格、挽き（豆のまま／挽き目番号）、店の風味説明、保存方法、開封日、タグ、写真
- 在庫は「入庫・抽出・調整・おすそ分け・廃棄」の履歴を積み上げて計算する。残量の根拠をいつでも追え、袋ごと量り直せば誤差を補正できる
- 残り日数は直近2週間の消費ペースから予測する
- 鮮度は「休ませ中 → 飲み頃 → ピーク後 → 早めに消費」の4段階で表示する。初期値は焙煎度ごとの目安（2章）で、評価が集まると豆ごと・焙煎度ごとに補正する
- 冷凍ストックは小分け容器単位（番号・量・冷凍日）で管理し、取り出すたびに通常在庫へ移す

### 4.4 珈琲問屋で買う前提の設計

珈琲問屋は受注後に焙煎し、焙煎度は8段階、挽き目は17段階から選べ、豆は100種類以上あります（[コーヒー豆研究所](https://coffee-labo.co.jp/?p=92488)）。この特徴に合わせて、登録・在庫・発注を最適化します。

- **焙煎度の表記を店と揃える**：ライト／シナモン／ミディアム／ハイ／シティ／フルシティ／フレンチ／イタリアンの8段階をそのまま選択肢にし、同じ表記で再注文できるようにする
- **生豆時の重量表記に対応**：例えばローストお試しメール便は生豆時100gで、焙煎後は約81〜84g（[楽天市場店](https://item.rakuten.co.jp/tonya/70924/)）。表記重量と到着時の実重量を分けて記録し、焙煎度ごとの目減り率を学習して次回から自動で推定する
- **焙煎日**：受注後焙煎なので、発送日を焙煎日の目安にする。袋に焙煎日があればそちらを優先
- **再注文リンク**：商品ページのURLを豆カードに保存し、「同じ豆・同じ焙煎度で注文」ボタンから店のページを開く。注文そのものは店のサイトで行う
- **豆情報の取り込み（無料）**：アプリから店のページを直接読み込むことはブラウザの仕組み上できないため、①商品ページの文章を貼り付けると項目に自動で振り分ける、②注文確認メールを貼り付けると注文した豆をまとめて在庫登録する、の2通りにする
- **発注タイミング**：注文日・発送日・到着日からお届けまでの日数を学習し、「在庫が切れる日 − お届け日数 − 休ませる日数」を発注推奨日として知らせる
- **送料の最適化**：送料と送料無料ラインは設定欄に入れておき（店の案内を見て入力）、在庫切れ予測と冷凍庫の空きから、ラインに届くまとめ買い案を出す
- **焙煎度違いの飲み比べ**：同じ豆を4つの焙煎度（ミディアム・ハイ・シティ・フルシティ）で届けるお試しセットがある（[楽天市場店](https://item.rakuten.co.jp/tonya/70924/)）。アプリの「焙煎度比較モード」で同じレシピ・ブラインドで評価し、産地ごとの好きな焙煎度を学習して、次の注文で「この豆はハイローストで」と提案する

### 4.5 器具と水

- ドリッパー：形状（円錐・台形・平底・ウェーブ）、穴の数、素材
- フィルター：紙・布・金属、漂白か無漂白か、銘柄
- グラインダー：刃の種類（コニカル・フラット）、目盛りの刻み、ゼロ点（刃が触れる位置）。ゼロ点を記録しておくと、清掃や分解の後の目盛りのズレを補正できる
- グラインダー目盛り表：目盛りと粒度の目安を対応させ、別のグラインダーでも同じ挽き目を再現できるようにする
- 水：名前（例：水道水＋浄水器）、硬度、アルカリ度、TDS、pH。SCA基準（2章）との差を表示する

## 5. 分析機能の詳細

分析は「今日の判断に使うホーム」と「好みを知る深掘り」の2層です。データが少ないうちは誤解を招かないよう、どの数字にも件数と信頼度を添えます。

### 5.1 指標の定義

| 指標 | 計算方法 | 使い道 |
| --- | --- | --- |
| 比率 | 湯量 ÷ 粉量（1:x） | レシピの基本 |
| 抽出収率 | TDS(%) × 抽出液の重さ ÷ 粉量 | 抽出の進み具合 |
| 推定抽出液量 | 湯量 − 保持率 × 粉量（保持率の初期値2.0、器具ごとに実測で学習） | 抽出液を量らない日の代用 |
| 焙煎後日数 | 抽出日 − 焙煎日 | 飲み頃の分析 |
| 1杯の原価 | 粉量 × 豆のg単価（到着時の実重量で計算） | コスト管理 |
| カフェイン推定 | 抽出液量(mL) × 0.6mg × 15 ÷ 実際の比率。成分表の「比率1:15で100mLあたり60mg」からの換算で、あくまで目安 | 1日の摂取量の把握 |
| 自分の理想ゾーン | 評価上位の抽出のTDSと抽出収率の範囲（TDS付きの記録が10件を超えたら表示） | 次の抽出の目標 |
| 再現性 | 同じ豆・同じレシピでの評価とTDSのばらつき（標準偏差） | 腕と器具の安定度 |
| 嗜好スコア | カテゴリごとの平均評価を件数で補正（下の式） | 好きな産地・精製・焙煎度 |
| ダイヤルインの速さ | 豆ごとに、自己ベストの9割に届くまでにかかった杯数 | 新しい豆への対応力 |

嗜好スコアはベイズ平均を使い、件数の少ないカテゴリを全体平均に寄せて「1杯だけ飲んだ豆が1位」という誤認を防ぎます（n = そのカテゴリの杯数、m = 事前の重みで初期値5）。

```latex
\text{score}_c = \frac{n_c \, \bar{x}_c + m \, \bar{x}_{\text{all}}}{n_c + m}
```

### 5.2 分析画面

| 画面 | 分かること | 図の形 | 使えるようになる目安 |
| --- | --- | --- | --- |
| ホーム（今日） | 今日のおすすめ、在庫の豆ごとの飲み頃、残量、直近の抽出 | カード＋飲み頃の帯グラフ | 初日から |
| ダイヤルインの道のり | 豆ごとに何を変えて評価がどう動いたか | 杯数×評価の折れ線＋変えた条件の注記 | 1つの豆で3杯〜 |
| 抽出チャート | 自分の好きな濃度と抽出収率の範囲 | TDS×抽出収率の散布図、比率の斜線、点の色＝評価 | TDS付き10件〜 |
| 条件と評価 | 挽き目・湯温・比率・焙煎後日数のどれが評価を動かすか | 散布図＋傾向線 | 20件〜 |
| 飲み頃カーブ | 焙煎度ごとに何日目が一番おいしいか | 焙煎後日数×評価の折れ線 | 同じ焙煎度で5袋〜 |
| 嗜好マップ | 産地×焙煎度、精製×焙煎度の好み | ヒートマップ（セルに件数を表示） | 30件〜 |
| 味の好みの位置 | 酸味・甘さ・苦味・ボディの「ちょうど良い」強さ | 属性ごとの強度×好みの散布図と山の頂点 | プロ評価20件〜 |
| 生活との関係 | 時間帯・曜日・気分と評価や選んだ豆 | 横棒グラフ | 30件〜 |
| カレンダーとカフェイン | 毎日の杯数、カフェイン推定量の推移 | カレンダー型ヒートマップ＋日別の棒グラフ | 初日から |
| 再現性 | 同じレシピでのブレが許容範囲内か | 管理図（平均と±2σの線） | 同一レシピ8杯〜 |
| コスト | 月の支出、1杯単価、焙煎度・銘柄ごとの満足度あたり価格 | 月別の棒グラフ＋一覧表 | 1か月〜 |

### 5.3 データが少ないときの作法

- 件数が目安に届かない画面は「あと○杯で表示」と出し、途中の不安定な結果を断定しない
- 初めは研究や業界の目安（2章）を表示し、自分のデータが貯まると「自分の値」に切り替える
- 相関は「一緒に動いている」だけで原因とは限らないと添え、確かめるための1変数実験（F7）を提案する

## 6. 提案エンジン

提案は「ルール（初日から）→ 統計（20杯から）→ AI相談（任意・無料）」の3層で、どれも根拠を表示し、1回に変えるのは1変数だけです。すべてブラウザの中で計算するので、費用はかかりません。

### 6.1 3層の仕組み

| 層 | 動き出す時期 | 仕組み | 提案の例 |
| --- | --- | --- | --- |
| ルール | 初日 | 抽出理論にもとづく「症状→直し方」の対応表（下の図） | 「酸っぱくて薄い → 挽き目を1目盛り細かく」 |
| 統計 | 20杯〜 | 自分のデータから、条件と評価の関係・理想ゾーン・嗜好スコアを推定 | 「あなたの評価は湯温より挽き目で動く。この豆は細かい側が好み」 |
| AI相談 | いつでも | データの要約と質問文をテキストにしてコピーし、手元のチャットAIに貼る（API料金ゼロ） | 「この3週間の記録から、次に試すべきことは？」 |

### 6.2 ダイヤルイン診断（ルール層の核）

1杯を「濃さ」と「抽出の進み具合」の2軸でマスに置き、マスごとの直し方を提案します。新しい抽出チャートでは、甘さは低濃度・低収率で、苦味は高濃度・高収率で最大になり、ベリーや柑橘は高濃度・低収率、紅茶のような味は低濃度・高収率に現れます（[SCA](https://sca.coffee/sca-news/coffee-decoded-14-dialling-in)）。

| 濃さ＼抽出 | 抽出が足りない | ちょうど良い | 抽出しすぎ |
| --- | --- | --- | --- |
| 濃い | 濃いのに酸っぱい：①湯を増やす ②細かく挽く（1杯に1つずつ） | 重い・濃すぎる：比率を薄くする（湯を増やす） | 苦くて重い・渋い：①湯を増やす ②粗く挽く（1杯に1つずつ） |
| ちょうど | 酸っぱい・余韻が短い：1目盛り細かく挽く（または湯温を2℃上げる） | 好みの1杯：そのまま続ける（甘さと酸味は注湯配分で） | 渋い・ドライ・えぐい：1目盛り粗く挽く（または攪拌を減らす） |
| 薄い | 薄くて酸っぱい：①粉を増やす ②細かく挽く（1杯に1つずつ） | 水っぽい：比率を濃くする（粉を増やす） | 薄いのに渋い：①粉を増やす ②粗く挽く（1杯に1つずつ） |

直す順番：縦のズレ（濃さ）を先に、横のズレ（抽出）を後に。1杯で変えるのは1つだけ。

中央のマスが目標で、周りの8マスは「次の1杯でどちらへ動かすか」を示します。角のマスは2つずれているので、濃さ→抽出の順に1杯ずつ直します。

- **マスの決め方**：屈折計がないときは、「濃さ」のJAR評価で縦、「酸味・余韻の短さ」と「苦味・渋み・ドライさ」のJAR評価で横を決める。屈折計があれば、実測のTDSと抽出収率を自分の理想ゾーンと比べる
- **直す順番**：濃さのズレを先に直す。好みを最も左右するのは濃度で（2章）、比率の変更は結果を読みやすいため
- **1回の変更幅**：挽き目1目盛り、比率±0.5（例：1:15 → 1:15.5）、湯温±2℃、粉量±0.5〜1g、蒸らし±10秒、注湯回数±1
- **自己較正**：変えた条件と、次の杯のJAR評価の動きを記録し、「このグラインダーは1目盛りで酸味が平均どれだけ動くか」を学習して、変更幅を自分用に調整する
- **根拠の表示**：①あなたの入力（症状）②理論（どのマスか）③あなたの実績（例：この豆で挽き目を細かくした3回中3回で酸味が下がった）④確信度、の4点を必ず並べる

### 6.3 新しい豆の初期レシピ

豆を登録したら、焙煎度・精製・産地・標高・品種が似ている過去の豆を探し、評価の高かったレシピの中央値を最初のレシピにします。似た豆がないうちは、焙煎度ごとの叩き台を使います（深煎りは85〜90℃を勧める例：[コーヒー豆研究所](https://coffee-labo.co.jp/?p=125612)、V60のレシピ例：粉15g・湯240mL・92℃ [コーヒー豆研究所](https://coffee-labo.co.jp/?p=900021)）。

| 焙煎度（珈琲問屋の表記） | 湯温の初期値 | 比率の初期値 | 挽き目の初期値 |
| --- | --- | --- | --- |
| ライト〜ミディアム | 92〜94℃ | 1:15〜1:16 | 中細持ち |
| ハイ〜シティ | 88〜92℃ | 1:15 | 中挽き |
| フルシティ〜イタリアン | 85〜88℃ | 1:14〜1:15 | 中〜やや粗め |

この表はあくまで初回の叩き台で、自分の評価が貯まると焙煎度ごとの「自分の初期値」に置き換わります。

### 6.4 今日の一杯

在庫の豆ごとに、自分のベストレシピを前提に点数を付け、上位3つを理由と一緒に出します。

- **予測評価**：嗜好スコアと、焙煎後日数による飲み頃の補正
- **在庫の事情**：ピークを過ぎそうな豆や、残りわずかの豆を優先して使い切る
- **文脈**：時間帯・気分プリセット・その日のカフェイン累計。就寝予定の何時間前から控えるかは自分で設定し、それ以降はカフェインレスや少量レシピを優先する
- **気分プリセット**：「目覚め（明るい酸味・やや濃いめ）」「くつろぎ（甘さ重視・やや薄め）」「食後（ボディ重視）」「来客（失敗しにくい定番レシピを杯数ぶん拡大）」など。狙いの味を診断マップの位置に置き換えて、比率や注湯配分を調整する

### 6.5 次に買う豆（珈琲問屋版）

- **候補**：店の商品ページから貼り付けて作った「気になる豆リスト」と、過去に買った豆
- **自分向け度**：産地・精製・焙煎度の嗜好スコアから予測する
- **開拓と定番のバランス**：飲んだことのない産地や精製には「開拓ボーナス」を付け、好きなものばかりに偏らないようにする（多腕バンディットの考え方）
- **焙煎度まで指定**：同じ産地で評価の高い焙煎度を添える（4.4の焙煎度比較の結果を使う）
- **発注メモ**：消費ペース・冷凍庫の空き・送料無料ライン・休ませる日数から、「いつ・何を・どの焙煎度で・何g」を1枚にまとめる。注文は店のサイトでこのメモを見ながら行う

### 6.6 実験プランナー

- **1変数の飲み比べ**：同じ豆で条件を1つだけ変えた2杯を、アプリが並べ順を伏せてブラインドで評価する
- **最適化モード**：挽き目と比率（必要なら湯温）の範囲を決めると、ベイズ最適化で「次に試すと最も学びが大きい条件」を提案し、少ない杯数で好みの山に近づく。計算はブラウザ内で完結

### 6.7 AI相談テキスト（API料金ゼロ）

- ボタン一つで、直近の抽出の要約表、嗜好スコアの上位と下位、在庫と飲み頃、質問文をまとめたテキストを作り、クリップボードにコピーする
- 質問のテンプレ：「次の1杯で何を変える？」「この豆に合う淹れ方は？」「次に珈琲問屋で何を買う？」
- 回答の形式を指定した一文を添えておき、AIの回答を貼り戻すと提案レシピとして取り込めるようにする
- データは自動ではどこにも送られず、貼るかどうかは自分で決める

## 8. 画面構成とUX

画面は下部の5タブ（ホーム・抽出・豆と在庫・分析・その他）で構成し、毎日使う抽出だけは迷わない一本道にします。

- ホーム：今日のおすすめ／飲み頃の帯／在庫アラート／直近の抽出
- 抽出（一本道）：レシピを選ぶ → 準備チェック → 注湯タイマー → 実績の確認 → テイスティング → 次の1杯の提案
- 豆と在庫：在庫一覧／豆の詳細／冷凍ストック／発注メモ／気になる豆
- 分析：ダッシュボード／抽出チャート／嗜好マップ／実験の結果／レポート
- その他：レシピ帳／器具と水／飲み比べ／書き出し・保存／設定／用語辞典

抽出タブはレシピ選びから次の1杯の提案まで一直線に進み、ほかのタブは一覧から2タップ以内で目的の画面に届きます。

### 8.1 抽出中の画面（いちばん作り込む所）

- 経過時間と「次の目標：累計150g／あと12秒」を画面の上半分に特大表示し、下半分はどこを押しても「注湯完了」になる
- 注湯の合図：開始3秒前からカウントダウン音、到達時に短い音と振動（振動は対応端末のみ）、読み上げ（「2投目、150グラムまで」）
- 前回のベストの注湯ペース（ゴースト）を重ねて、今回のズレを秒で表示
- 画面スリープ防止、暗い台所でもまぶしくない暗色テーマ、横向き対応
- タイマーは開始時刻からの差で計算し、別の画面を開いてもずれない

### 8.2 入力を速くする工夫

- 前回値の引き継ぎ、±ボタン、よく使う値のチップで、数字はほぼ打たない
- 数字を打つときは大きなテンキー型パッド
- 主要ボタンは親指の届く画面下部に置き、片手で完結させる
- 入力途中でアプリを閉じても、下書きを自動保存して続きから再開できる

### 8.3 見た目と安心

- 数字は等幅フォントで桁が揺れないようにし、文字は大きめ
- 色は意味にだけ使う（飲み頃・休ませ中・ピーク後・在庫わずか）。豆ごとに固定の色を付け、どの画面でも同じ色で見分ける
- ダーク／ライトは端末の設定に合わせて自動切替
- 削除は30日間取り消せる（ゴミ箱）。抽出中に戻る操作をしたら確認を出す

## 9. データモデル

データは14種類の記録に分け、在庫は「履歴の積み上げ」、抽出は「その時のレシピの写し」を持つ形にして、過去の記録が後から書き換わらないようにします。

| 記録 | 役割 | 主な項目 | つながり |
| --- | --- | --- | --- |
| Bean（豆） | 1袋ごとの豆 | 銘柄、購入先、商品URL、産地、品種、精製、標高、焙煎度、焙煎日、表記重量とその基準（生豆時／焙煎後）、実重量、価格、状態 | 注文・在庫履歴・抽出 |
| InventoryTx（在庫履歴） | 在庫の増減1件 | 日時、増減g、種類（入庫・抽出・調整・おすそ分け・廃棄・冷凍・解凍） | 豆・抽出 |
| FrozenPortion（冷凍小分け） | 冷凍庫の容器1つ | ラベル番号、g、冷凍日、取り出し日 | 豆 |
| Equipment（器具） | ドリッパー・フィルター・グラインダー等 | 種類、名前、属性。グラインダーは目盛りの刻み・ゼロ点・粒度の対応表 | レシピ・抽出 |
| WaterProfile（水） | 使う水の成分 | 名前、TDS、硬度、アルカリ度、pH | 抽出 |
| Recipe（レシピ） | 淹れ方の型 | 粉量、湯量、湯温、挽き目、蒸らし、注湯ステップ、目標時間、版番号と元の版 | 抽出 |
| Brew（抽出） | 1杯の記録 | 日時、豆、計画の写し、実績、豆の状態、状況、写真、計算値 | 豆・レシピ・評価 |
| Tasting（評価） | 1杯・1人・1温度の評価 | 評価者、温度帯、★とタグ、JAR、強度と好み、香味、雑味、メモ、ブラインドかどうか | 抽出・ゲスト |
| Suggestion（提案ログ） | 出した提案とその結果 | 種類、変える変数と幅、根拠、確信度、採用したか、次の抽出 | 抽出（自己較正に使う） |
| Experiment（実験） | 飲み比べや最適化 | 種類、仮説、対象の抽出、伏せた順番、結果 | 抽出 |
| Order（注文） | 珈琲問屋への注文1回 | 注文日・発送日・到着日、品目（銘柄・焙煎度・表記重量・価格）、送料 | 豆 |
| Wishlist（気になる豆） | 買う候補 | 商品URL、銘柄、産地、精製、価格、予測スコア | 豆（購入後） |
| Person（ゲスト） | 評価してくれる人 | 名前、メモ | 評価 |
| Settings（設定） | アプリ全体の設定 | 単位、評価の目盛り、送料と無料ライン、カフェイン設定、最終バックアップ日 | — |

- IDはランダムな文字列（UUID）にし、スマホとPCのデータを統合しても衝突しないようにする

- 項目名に単位を入れる（doseG、tempC、totalSec、tdsPct、priceJpy）
- 書き出しファイルにはデータ形式の版番号を入れ、形式が変わっても古いバックアップを読めるようにする

## 10. 技術構成

「1つのHTMLファイル＋端末内データベース（IndexedDB）」で作り、スマホでは無料のGitHub Pagesに置いてホーム画面に追加して使います。外部サービスは無料の天気APIだけで、なくても全機能が動きます。

- ブラウザの中（1つのHTMLファイル）：画面（5タブ・注湯タイマー・評価・グラフ）⇄ エンジン（記録・計算・在庫・分析、提案：ルール→統計→最適化。すべて端末内で計算）⇄ 端末内の保存（IndexedDB）。ブラウザの機能（スリープ防止・音と読み上げ・カメラとQR・印刷とPDF）を利用
- 外の世界（どれも無料・任意）：珈琲問屋のサイト（商品ページ・注文メールを貼り付け）→ 画面／天気API（Open-Meteo）→ エンジン／手元のチャットAI ⇄ エンジン（相談テキストのコピペ）／書き出しファイル（JSON・CSV・PDF・画像）⇄ 保存

計算も保存もブラウザの中だけで行い、外とのやり取りは、貼り付け・コピー・ファイルと無料の天気取得に限られます。

### 10.1 置き場所の3段階

| 段階 | 置き方 | できること | 注意 |
| --- | --- | --- | --- |
| 1 | HTMLファイルをPCで直接開く | 全機能の試作と確認 | スマホでは使いにくく、オフライン対応の仕組み（PWA）は動かない |
| 2 | GitHub Pagesに置く（公開リポジトリなら無料、HTTPS付き。[GitHub Docs](https://help.github.com/articles/what-is-github-pages)） | スマホのホーム画面に追加、オフライン動作 | 公開されるのはコードだけ。記録データは各端末の中にあり、ネットには出ない |
| 3 | 端末間の引っ越し | PCとスマホで同じデータを使う | 同期サーバーは使わず、ファイルかQRで移す（X13） |

### 10.2 データを失わないための対策

- 保存は容量の大きいIndexedDBを使う。localStorageは容量が小さく文字列しか保存できないため、写真や注湯の時系列に向かない
- **iPhoneは必ずホーム画面に追加して使う**：Safariで開くだけだと、そのサイトを触らないままSafariを7日使うとIndexedDBを含む保存データが削除される。ホーム画面に追加したアプリはこの対象外（[web.dev](https://web.dev/articles/storage-for-the-web)）。アプリ側でも未追加なら警告を出す
- 起動時に「消されにくい保存」（navigator.storage.persist）を要求する
- 写真は保存前に縮小して容量を抑える
- バックアップは三重化：①一定件数ごとの書き出しの促し（G2）②PCでは決めたフォルダへの自動保存（X1）③復元時はIDと更新日時で差分だけ統合

### 10.3 ブラウザ機能の対応状況

| 機能 | iPhone（Safari） | Android（Chrome） | PC（Chrome・Edge） | 使えないときの代わり |
| --- | --- | --- | --- | --- |
| 画面スリープ防止（Screen Wake Lock） | 対応。ホーム画面に追加したアプリではiOS 18.4以降（[Progressier](https://progressier.com/pwa-capabilities/screen-wake-lock)） | 対応 | 対応 | 端末の自動ロック時間を延ばす |
| Bluetoothスケール（Web Bluetooth） | 非対応（[Web Platform Features](https://web-platform-dx.github.io/web-features-explorer/features/web-bluetooth)） | 対応 | 対応 | 手入力とタップ式のラップ記録 |
| NFCタグ（Web NFC） | 非対応 | 対応（[Chrome for Developers](https://developer.chrome.com/docs/capabilities/nfc?hl=ja)） | 非対応 | QRラベル（X14） |
| 通知 | ホーム画面に追加した場合のみ（[Ionic](https://ionic.io/blog/wp-json/wp/v2/posts/4945)） | 対応 | 対応 | アプリを開いている間の画面内リマインド |
| 決めたフォルダへの自動保存 | 非対応 | 非対応 | 対応 | ファイルのダウンロード保存 |

スマホの機種で使える機能が変わるため、各機能は「使えるかを確かめてから表示する」作りにします（12章で端末を確認）。

### 10.4 使う部品（すべて無料）

- 画面：フレームワークなしの素のJavaScript。ビルド作業が不要で、AIに直してもらうときも扱いやすい
- 保存：IndexedDBを扱いやすくするライブラリ（Dexie.js）
- グラフ：Chart.js（散布図・折れ線・棒グラフ）
- QR：QRコードの生成と読み取りのライブラリ
- 文字認識：Tesseract.js（端末内で処理し、画像を外に送らない）
- 天気：Open-Meteo。非商用ならAPIキー不要・無料で1日10,000回まで、データの出典表示が必要（[Open-Meteo](https://open-meteo.com/?lat=47.7&lon=3.4458)）。位置情報の許可は使わず、設定した地点だけを問い合わせる
- 最適化：ベイズ最適化は小さな自前実装で、ブラウザ内で計算する

### 10.5 品質の保ち方

- 比率・抽出収率・在庫・カフェインなどの計算は、答えの分かっている例で自動テストする
- 「デモデータ100杯」を生成する機能を作り、分析画面をデータが貯まる前に確認できるようにする
- 書き出し→全削除→復元で、データが1件も欠けないことを確かめる

## 11. 実装ロードマップ

4段階で作り、各段階の終わりに完了条件を置きます。段階ごとの対象は3章・7章の優先度（MVP／v1／v2／将来）にそのまま対応するので、優先度を入れ替えれば計画も変わります。

- 段階1 MVP「毎日記録できる」：抽出の記録とタイマー／豆の登録と残量／JAR評価と直し方／バックアップ → 完了条件1：7日続けて毎回30秒以内に記録できる
- 段階2 v1「好みが見える」：分析画面と好みの地図／スマホのホーム画面化／珈琲問屋の取り込み／今日の一杯・冷凍管理 → 完了条件2：20杯の記録で根拠付きの提案が出る
  - 段階2の終わりに総点検（2-8）を入れ、段階3に入る前に全機能のデバッグと、見た目・動きの調整をする
- 段階3 v2「賢く提案する」：実験プランナー／次に買う豆の提案／ブラインド評価／豆袋の文字読み取り → 完了条件3：提案どおりに淹れた杯の評価が上がる
- 段階4 将来「広げる」：スケール連携／カフェ巡りログ／豆の図鑑PDF／実績バッジ

最初のMVPは「毎日の記録が苦にならないこと」だけを目標にし、分析や提案はデータが貯まってから効いてくる順番に並べています。

## 13. 付録

### 13.1 用語集

| 用語 | 意味 |
| --- | --- |
| TDS（濃度） | 抽出液に溶けている成分の割合。濃さの指標 |
| 抽出収率（EY・PE） | 粉の重さのうち、液に溶け出した割合。抽出の進み具合の指標 |
| 比率 | 湯量 ÷ 粉量。1:15なら粉1gに湯15g |
| 保持率（LRR） | 抽出後の粉に残る液の量。透過式で粉1gあたり約2g |
| JAR | 「ちょうど良い」を中心に、弱すぎ・強すぎで評価する方法 |
| CATA | 当てはまる言葉に全部チェックする評価方法 |
| CVA | SCAが2024年に採用した、描写と好みを分ける新しい評価の仕組み |
| レスト | 焙煎後に豆を休ませる期間。炭酸ガスが抜けて味が落ち着く |
| 蒸らし | 最初に少量の湯で粉全体を湿らせ、ガスを抜く工程 |
| 落ち切り（ドローダウン） | 最後の注湯から液が落ち切るまでの時間 |
| 微粉 | 挽いたときに出るとても細かい粉。詰まりや雑味の原因になりやすい |
| PWA | ホーム画面に追加でき、オフラインでも動くWebアプリ |
| IndexedDB | ブラウザの中にある端末内データベース |
| ブックマークレット | ブックマークに登録して、開いているページの上で動かす小さなプログラム |

### 13.2 最初から入れておく選択肢

- 焙煎度：ライト／シナモン／ミディアム／ハイ／シティ／フルシティ／フレンチ／イタリアン
- 精製：ウォッシュト／ナチュラル／ハニー／スマトラ式／アナエロビック／その他（自由入力）
- 品種：ティピカ／ブルボン／カトゥーラ／カトゥアイ／ゲイシャ／SL28／パカマラ／その他
- ドリッパー：V60／カリタウェーブ／オリガミ／KONO／ケメックス／ハリオ スイッチ／その他
- 注ぎ方：中心／円／の字／スワール／攪拌
- 気分・目的：目覚め／集中／くつろぎ／食後／来客
- 雑味タグ：えぐい／紙っぽい／焦げ／古い／水っぽい
- レシピの雛形：4:6メソッド（前半40%・後半60%を自動計算）／蒸らし＋2〜3回注湯の基本形

### 13.3 AIコーディングツールに渡す実装指示（MVP）

Claude Codeなどにこの設計書と一緒に渡すと、MVPを作り始められます。

```markdown
# 依頼：コーヒー記録アプリ「Pourfolio」のMVPを実装してください

## 前提
- 個人利用。費用ゼロ（サーバー・有料API・課金なし）
- index.html 1つで完結。フレームワークなし（素のJavaScript）、ビルド不要
- データはIndexedDB（Dexie.js）に保存し、全データをJSONで書き出し・復元できること
- スマホ縦画面を最優先。抽出中は大きな文字とボタン、画面スリープ防止（Screen Wake Lock）
- 日本語UI。豆の購入先は珈琲問屋（焙煎度8段階・生豆時の重量表記に対応）

## 作る範囲（設計書3章の優先度MVP）
A1〜A4、B1〜B2、C1〜C3、D1、E1、F1、G1〜G2

## データ（設計書9章）
Bean / InventoryTx / Equipment / Recipe / Brew / Tasting / Settings を実装。
- IDはUUID。全記録に createdAt / updatedAt / deletedAt
- 在庫は InventoryTx の合計で計算
- 項目名に単位を入れる（doseG, tempC, totalSec）

## 提案ロジック（設計書6.2）
JAR評価（-2〜+2）から「濃さ×抽出」の3×3に分類し、濃さのズレを先に、1回1変数で提案する。
根拠（入力・理論・過去の実績・確信度）を必ず表示する。

## 受け入れ条件
- 前回コピーから3タップ・30秒以内で1杯を記録できる
- 抽出のたびに豆の残量が減り、残り杯数が表示される
- 書き出し→全削除→復元で、データが1件も欠けない
- 比率・推定抽出液量・カフェイン推定の計算に自動テストがある
```
